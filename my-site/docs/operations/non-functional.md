# Нефункциональные требования

## Производительность

- API пользовательских сценариев (ввод метрик, получение рекомендации) должно отвечать в пределах SLA.
- Список клиентов тренера поддерживает пагинацию и сортировку на стороне backend.
- Расчёт Readiness Index в n8n должен завершаться в течение 5 секунд с момента сохранения метрик.

## Надёжность

- Система обеспечивает повторяемость обработки Kafka-событий.
- POST /health-data поддерживает идемпотентность через `X-Idempotency-Key`.
- Интеграции с внешними сервисами (OneSignal) имеют retry-механизм.

## Безопасность

- Все защищённые методы API доступны только после аутентификации (JWT Bearer Token).
- Разграничение доступа строится на ролях: CLIENT, TRAINER, ADMIN.
- Тренер может просматривать только клиентов, связанных с ним через `trainer_client`.
- Персональные данные конечных клиентов не покидают контур партнёра.

## Масштабируемость

- Архитектура поддерживает рост числа партнёров и пользователей.
- Асинхронные потоки (Kafka) масштабируются независимо от мобильного API.
- При росте числа партнёров — горизонтальное масштабирование Backend API.
